# DXIL-side typed-buffer lowering into MSC: feasibility research

Baseline: `fc53082a8c17abbbaf282cbec700465f2b364c53`; source inspection on 2026-10-01.
Scope: evaluation only, before MSC compilation; no AIRCONV fallback, generated-AIR edits, production implementation, builds, or GPU runs.
Labels: **source fact** means inspected specification/code; **hypothesis** means proposed behavior not demonstrated; **recorded evidence** means an existing repository report, not a rerun here.

## Finding and decision

A private DXIL coordinate adjustment is the preferred candidate for a bounded binary-transform experiment: retain typed resource operations, supply per-view origin/count through a sidecar, and compile the modified DXIL with MSC. Retaining typed operations avoids rebuilding native format conversion and subword software stores; general correctness remains a hypothesis, not a repair.
A general typed-to-raw conversion is substantially harder: descriptor formats are runtime data, and packed stores introduce word-level interference between otherwise separate elements. Neither route currently justifies changing capability bits.
Synthetic R32_UINT source prototypes and bounded R8_UINT/R16_UINT typed-origin cases now have recorded GPU evidence below. The next gate should be a validated, unchanged DXIL round-trip, followed by an actual binary-to-binary R32_UINT coordinate transform. A later implementation would require separate authorization.

## Bounded synthetic GPU result, separate from binary-transform validation

**Recorded evidence, not rerun here:** [D3D12_DXIL_TYPED_BUFFER_LOWERING.md:82](D3D12_DXIL_TYPED_BUFFER_LOWERING.md#L82) reports two independently compiled synthetic HLSL routes: raw R32_UINT addressing and typed R32_UINT coordinates with an explicit origin CBV. Each matched 30/30 native GPU cases: UAV load/store, SRV load and atomic add; FirstElement 0/1/4/257/260; BoundsCheck disabled/enabled. The report records full-allocation prefix/suffix checks and Metal API/GPU validation.
The same typed-origin binaries also matched 20/20 R8_UINT and 20/20 R16_UINT SRV/UAV cases, using unsigned boundary vectors including 128/255 and 256/65535. Both normal and no-private native probes repeated all 100 cases successfully. No subword atomic was tested.
The typed prototype declares private origin/count at [dxil_typed_buffer_lowering.hlsl:16](../tests/dx12/dxil_typed_buffer_lowering.hlsl#L16) and applies origin to accesses at lines 39–45. These are freshly compiled source shaders, not modified existing DXIL binaries. The prototype register b0/space1 is not a production reservation or a demonstrated collision-free mapping.
**Supported conclusion:** MSC can execute these explicit R32_UINT address expressions correctly in the tested native compute cases. This increases confidence in a typed-origin experiment; it does not validate automatic handle provenance, sidecar mapping, container assembly/validation, or runtime integration.
No broader format support follows: R32_FLOAT/SINT, normalized/half/packed formats, dynamic format binding, logical OOB/overflow/null behavior, concurrent aliases and subword CAS, static/volatile metadata generations, graphics and other atomic operations remain unvalidated. An in-bounds prototype containing guards does not exercise those guards' OOB behavior. Existing companion-padding failure evidence remains distinct.

## DXIL dialect and container validity

**Source fact:** DXIL uses LLVM 3.7-era bitcode with additional semantics. Modern LLVM upgrades old bitcode; DXIL emission needs its specialized writer and preparation passes. Thus ordinary LLVM 15 `llvm-dis`/`llvm-as` success is insufficient: upgraded pointer/attribute/metadata forms and ordinary newer bitcode emission are not automatically valid DXIL. Current LLVM architecture documentation describes newer infrastructure, not a guarantee that LLVM 15 has it. [LLVM architecture](https://llvm.org/docs/DirectX/DXILArchitecture.html)

**Source fact:** `IDxcAssembler::AssembleToContainer` accepts textual IR or bitcode; `IDxcValidator::Validate` exposes a distinct validation result. Both API HRESULT and `IDxcOperationResult` status/errors must be checked. The local declarations are [dxcapi.h:879](../tools/dxc/inc/dxcapi.h#L879) and [line 943](../tools/dxc/inc/dxcapi.h#L943). [DXC API](https://github.com/microsoft/DirectXShaderCompiler/blob/main/include/dxc/dxcapi.h)
The DXC assembler loads DXIL metadata and serializes through DXC machinery; it is not a generic adapter that repairs arbitrary modern IR. Prefer an isolated tool using a pinned DXC-compatible IR reader/writer, or demonstrate exact dialect-preserving text edits on a restricted corpus. [Assembler implementation](https://github.com/microsoft/DirectXShaderCompiler/blob/main/tools/clang/tools/dxcompiler/dxcassembler.cpp)

**Source fact:** a container includes the DXIL program/bitcode headers plus other parts; PSV0 describes pipeline validation, RDAT runtime data, and RTS0 a root signature. They are not interchangeable with the LLVM module. Validate lengths, part offsets, versions, resource declarations and entry-point shape before transformation. [Container format](https://llvm.org/docs/DirectX/DXContainer.html)
DXC emits PSV0 for ordinary shaders and RDAT for libraries, plus feature/signature/reflection/hash-related information as appropriate. Adding a sidecar resource or changing typed resources to raw requires corresponding metadata/container regeneration; preserve or deliberately regenerate applicable reflection, root-signature and debug parts rather than transplanting stale payloads. [Container assembler](https://github.com/microsoft/DirectXShaderCompiler/blob/main/lib/DxilContainer/DxilContainerAssembler.cpp)
PSV validation compares resource binding records/counts and shader properties with the module. A container-builder part replacement does not itself update these semantics. Require full-container validation, not just `ModuleOnly`, before independent MSC import. Libraries/RDAT should be excluded from the first bounded experiment and handled separately later. [Container validator](https://github.com/microsoft/DirectXShaderCompiler/blob/main/lib/DxilValidation/DxilContainerValidation.cpp)

## Resource identity and dynamic format binding

**Source fact:** `dx.resources` contains resource class/range/space/kind and element-type information; it does not encode each runtime descriptor's complete DXGI format. Typed buffer coordinates use elements, raw coordinates use bytes, and resource handles can be dynamically indexed. `GetDimensions` and load-status results are also observable. [DXIL specification](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst)
The actual SRV/UAV format resides in the descriptor; buffer SRVs additionally carry FirstElement, NumElements, stride and flags, and SRVs can remap components. [SRV descriptor](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_shader_resource_view_desc), [buffer SRV](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_buffer_srv), [UAV descriptor](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_unordered_access_view_desc)
**Inference:** `Buffer<float>` cannot be specialized once to a single storage width/normalization merely from its DXIL scalar type. A raw implementation needs either per-descriptor format dispatch or binding-dependent shader specialization with complete cache invalidation; volatile/direct-indexed descriptors make the latter particularly complex.

## Candidate A: typed coordinates plus private sidecar origin

**Hypothesis:** bind an aligned wider texture view into the original typed slot, then transform each typed load/store/atomic coordinate from `i` to `i + origin_elements`. MSC still performs typed conversion on the same underlying allocation. For a native origin `N` and desired byte origin `D`, use `(D-N)/texel_bytes` only when integral; a whole-buffer view is an alternative whose origin can be much larger.
Do not double-apply a future converter padding fix: pin the converter behavior and transformation ABI in the cache key, and verify whether descriptor padding must be zeroed for this route.
Logical bounds must be checked against original NumElements **before** addition, with overflow-safe arithmetic. A wider native view otherwise exposes prefix/suffix storage. Return logical dimensions; preserve required OOB, status, store-mask and atomic behavior. Null and sparse/tiled resources need separate policies; exclude unproven cases from an MVP.

**Hypothesis:** add a reserved private CBV/SRV for sidecar records through a translated internal root signature; retain the application's external signature and map it explicitly. Arbitrary private `dx.op` calls or treating an opaque handle as a pointer to MSC descriptor bytes would not constitute validated DXIL.
Each record should associate descriptor identity/generation with native-origin delta and logical count; raw lowering would additionally need format, bytes-per-element, component mapping and flags. Sidecar addressing must reproduce binding-space/range/index semantics, including handle PHIs/selects, nonuniform indexing and eventually heap indexing. Start with finite SM6.0 descriptor tables; reject unsupported handle flows.
The installed companion header locally encodes byte count, an eight-bit padding field and typed state at `/usr/local/include/metal_irconverter_runtime/metal_irconverter_runtime.h:834–863`; this is inspection of that SDK, not a public DXIL ABI. Prefer an explicitly bound sidecar over depending on undocumented handle representation. [Apple integration guidance](https://developer.apple.com/metal/shader-converter/)

**Source fact:** current root-argument translation maps application tables to MSC addresses at [d3d12_command_list.cpp:2873](../src/d3d12/d3d12_command_list.cpp#L2873). Backend/volatility are stored per use at [d3d12_command_encoder.hpp:33](../src/d3d12/d3d12_command_encoder.hpp#L33).
**Required design invariant:** create/update/copy/clear native view and sidecar together. Snapshot them under the same lock, preserve self-copy, and retain immutable submission versions through GPU completion. Volatile final descriptors must resolve matching final sidecars; static descriptors must retain their recorded version. Updating shared sidecar bytes while an earlier submission reads them is insufficient.
Existing ownership points are [ResolveDescriptors:426](../src/d3d12/d3d12_descriptor_heap.cpp#L426), [CopyDescriptors:670](../src/d3d12/d3d12_descriptor_heap.cpp#L670), and [submission retention:3276](../src/d3d12/d3d12_command_list.cpp#L3276). The sidecar would be a coordinated shader/binding change, not a shader-only patch.

## Candidate B: typed-to-raw lowering

**Source fact:** typed resources perform format conversion; raw views expose underlying bits. UNORM HLSL/resource compatibility is an explicit typed-load requirement. [Resource semantics](https://learn.microsoft.com/en-us/windows/win32/direct3d11/direct3d-11-advanced-stages-cs-resources), [typed UAV loads](https://learn.microsoft.com/en-us/windows/win32/direct3d12/typed-unordered-access-view-loads)
**Hypothesis:** an R32_UINT/SINT/FLOAT-only path can use byte addresses and appropriate bit reinterpretation on the original buffer. Preserve original logical bounds, component mapping/defaults and dimensions; translate supported typed atomics to corresponding raw atomics without changing returned old values or ordering. SM6.0 and later raw-operation availability must be respected rather than silently upgrading shader models.
Resource declarations, handle annotations where present, operation overloads/masks/alignment, shader flags and validation parts must agree with the new raw kind. Changing only an opcode is inadequate. Stage-specific restrictions and globally coherent/ROV properties also remain obligations.

For R8/R16, normalized/half and packed formats, reconstruct signedness, normalization, rounding, NaNs/denorms and channel packing from runtime format information. These differ from a numerical cast of an R32 word. [DXGI format definitions](https://learn.microsoft.com/en-us/windows/win32/api/dxgiformat/ne-dxgiformat-dxgi_format)
**Hypothesis, not established correctness:** use aligned word loads and a masked CAS loop for subword writes so neighboring elements are not lost through naive load/modify/store. CAS is a word-granularity operation, not an automatic proof of typed semantics. [Raw-buffer compare-exchange](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-rwbyteaddressbuffer-interlockedcompareexchange)
Mixed raw/typed/overlapping views must refer to the same allocation, with compatible synchronization and atomic behavior. CAS-expanded accesses can touch bytes outside the logical subview, potentially even beyond a tail allocation; require safe backing coverage without inventing logical visibility. Concurrent neighboring writes, typed atomics and buffer/texture aliases need explicit GPU tests. Do not invent subword typed atomic support or replace the shared allocation with an unsynchronized shadow buffer.

## Evidence required before implementation or support claims

1. Pin DXC/validator/MSC versions; inspect installed assembler/validator availability. Round-trip unchanged finite SM6.0 compute containers, then validate added sidecar resources and private signatures; reject stale PSV/reflection and unsupported libraries/RDAT.
2. Validate transformed R32 typed SRV/UAV load/store/atomic shaders, independently import into MSC, and compare CPU-seeded outputs plus entire allocation sentinels. Exercise origin zero, small unaligned origins, origins beyond eight-bit padding, OOB/overflow/null and logical dimensions.
3. Test dynamic descriptor arrays/nonuniform indices and two formats bound to the same shader; test static/volatile, copy/self-copy/overwrite, unavailable-to-valid late updates, repeated execution and concurrent in-flight sidecar generations.
4. Prove alias coherence and barriers with typed/raw/overlapping views before widening scope. Raw conversion additionally needs neighboring subword contention, packed conversions and edge-value rounding coverage; exclude unsupported atomics, tiled resources, heap handles and stages explicitly.

No transformed container or binary-transform MSC import was validated, and no GPU runs were performed by the research subagent. The main agent's recorded results establish only the synthetic integer compute cases described above; source feasibility and prototype execution do not establish end-to-end lowering correctness. Keep current rejection and capability reporting until these gates pass.
